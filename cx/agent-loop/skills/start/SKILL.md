# harness-agent-loop for Codex

ユーザーの依頼に対し、以下のオーケストレーション手順に従って開発を開始または再開する。

## 対象の依頼と作業場所

- 現在の会話にある具体的な開発依頼を使う。依頼がない場合だけ、作りたいもの、または再開したい作業をユーザーに確認する。
- 作業対象はユーザーが開いているプロジェクトとする。対象プロジェクトの `AGENTS.md`、`CLAUDE.md`、既存の `docs`、実行方法を確認する。
- 成果物は対象プロジェクトに保存し、プラグインのインストール先には書き込まない。
- この Skill と同じディレクトリの `references/planner.md`、`references/generator.md`、`references/evaluator.md` を各役割の指示として使う。Claude Code のエージェント登録名やモデル指定は使わない。
- サブエージェント機能が利用できる場合は各 Step の作業を対応する役割へ委譲し、対象 Sprint、読み書きするファイル、役割定義の内容、完了報告の要件を渡す。進捗 README の編集はメインエージェントだけが行う。
- サブエージェント機能が利用できない環境では、メインエージェントが役割を Step ごとに切り替えて進める。Evaluator の Step では実装者の自己評価だけで合格にせず、契約条件を独立に確認する。
- ブラウザ評価は利用可能なブラウザ操作手段を使う。実操作できない条件は未検証とし、合格と記録しない。
## 進捗管理（メインエージェント専任）

`docs/020_スプリント/README.md` を全スプリントの進捗の正本とする。**このファイルの作成・更新は、このSkillを実行しているメインエージェントだけが行う。** Planner、Generator、Evaluator に編集させてはならない。

開始または再開時に、メインエージェントは対象プロジェクトの `docs/020_スプリント/README.md` を読む。存在しなければ、このSkillに同梱した `references/sprint-progress-readme.md` を基に作成し、プレースホルダーを実際のスプリント情報へ置き換える。

1. `# スプリント進捗ステータス`
2. ステップ定義（Step 1〜5、担当、内容）
3. `## 一覧`（Sprint、概要、状態、契約ファイル）
4. `## 各スプリント詳細`（スプリントごとの Step、ステータス、完了日、備考）
5. `## 更新ルール`（本セクションのルール）

各スプリントの詳細表は次の形にする。

```markdown
### Sprint N

| Step | ステータス | 完了日 | 備考 |
|---|---|---|---|
| 1 planner | 未着手 | | |
| 2 契約起票 | 未着手 | | |
| 3 契約承認 | 未着手 | | |
| 4 実装 | 未着手 | | |
| 5 最終判定 | 未着手 | | |
```

### 更新タイミング

- サブエージェントへ作業を渡す直前に、該当 Step を「着手中」にする。備考には、現在残っている作業を簡潔に書く。
- サブエージェントから成功・未完了・失敗のいずれの報告を受け取った場合も、**次の委譲やユーザーへの最終報告より先に**該当スプリントの表を更新する。
- 報告内容と成果物を確認し、必要な成果が揃った Step だけを「完了」とする。完了日に `YYYY-MM-DD` を記録し、備考を空にする。未完了・失敗なら「着手中」のまま、残タスクまたは失敗理由を備考に書く。
- 差し戻しの場合、判定側の Step を「着手中」のままにして備考へ差し戻し理由を要約する。修正を委譲する直前に、修正側の Step も「着手中」に戻し、残タスクを書く。
- 作業を中止した Step は「中止」とし、備考に理由と後続作業の参照先（あれば）を書く。後続 Step も実施しない場合は、それぞれ「中止」として理由または参照先を書く。
- Step 5 が合格したときは、Step 5 を「完了（合格）」、完了日を当日、備考を空欄にし、同じ更新で「一覧」の状態を「完了」にする。
- Step 5 が不合格の間は「着手中」とし、備考には未解決事項だけを要約する。スコア、テスト手順、改善提案などの判定詳細は載せない。

### 記載制約

- 基本ステータスは「未着手／着手中／完了／中止」の4種とする。Step 5 の合格時だけ、合格を明示するため「完了（合格）」と記載する。
- 「完了」「完了（合格）」「未着手」の備考は必ず空欄にする。
- 「着手中」の備考には、差し戻し理由・残タスクなど、未完了の内容だけを書く。
- 「中止」の備考には理由と、後続作業の参照先（該当する場合）を書く。
- 一覧の状態は、Step 5 が「完了（合格）」になるまで「着手中」とする。中止時は「中止」とする。
- Evaluator の判定詳細（契約レビュー結果、テスト結果、スコア、改善提案）は、Evaluator が各 `sprint-N.md` の末尾へ追記する。進捗 README には転記しない。
- 更新後は、一覧と詳細の Sprint 番号、リンク、状態が一致し、完了・未着手行の備考が空であることを読み直して確認する。この確認が終わるまで次のサブエージェントへ委譲しない。

## 設計方針

Anthropic の [Harness Design for Long-Running Apps](https://www.anthropic.com/engineering/harness-design-long-running-apps) に基づく。

Generator（機能と見た目）と Evaluator（採点）の2者ループを基本とする。Generator は仕様の方針に沿って一貫したビジュアル方針を決め、Evaluator の採点フィードバックを受けて改善する。

## エージェント構成

| エージェント | 役割 | 主な出力 |
|---|---|---|
| Planner | 仕様書・スプリント計画の策定 | `docs/010_製品仕様書/spec.md`、`docs/020_スプリント/sprint-N.md` |
| Generator | スプリント契約の起票、機能とUIの実装 | 動作するアプリケーションコード |
| Evaluator | 契約レビュー、ブラウザ操作による機能・デザイン評価 | 合格・不合格判定レポート |

標準パイプライン:

```text
Planner → Generator（契約起票）⇄ Evaluator（契約承認）→ Generator（実装とUI）→ Evaluator（最終判定）
                                                                ↑                         │
                                                                └──── 不合格時の修正 ────┘
```

契約は Generator が起票し、Evaluator が承認する。Planner は機能とゴールまでを定義する。

## オーケストレーション手順

### 1. Plannerによる仕様策定

- 新規開発または機能追加の依頼を受けたら開始する。
- メインエージェントが Sprint N を採番し、進捗 README の一覧へ「着手中」として追加する。詳細表を追加して Step 1 を「着手中」にする。
- `docs/010_製品仕様書/spec.md` と `docs/020_スプリント/sprint-N.md` を作成する。
- スプリントには機能とゴールを記載し、契約条件は空欄にする。
- Planner の報告と成果物を確認し、完了ならメインエージェントが Step 1 を「完了」に更新する。未完了なら「着手中」のまま残タスクを書く。
- ユーザーが仕様を承認してから次へ進む。

### 2. Generatorによる契約起票

- `sprint-N.md` に機能とゴールが記載されていることを確認する。
- メインエージェントが Step 2 を「着手中」に更新する。
- Generator に「Sprint N の契約を起票してください。実装はまだ行わないでください」と指示する。
- Generator は「何を作るか」「成功をどう検証するか」をテスト可能な条件として `sprint-N.md` に記載する。
- Generator の報告と成果物を確認し、完了ならメインエージェントが Step 2 を「完了」に更新する。未完了なら「着手中」のまま残タスクを書く。

### 3. Evaluatorによる契約レビュー

- メインエージェントが Step 3 を「着手中」に更新する。
- Evaluator に「Sprint N の契約を実装前レビューしてください」と指示する。
- 仕様適合、テスト可能性、曖昧さ、矛盾を確認させる。
- Evaluator の報告を受け取ったら、メインエージェントが進捗 README を更新する。承認なら Step 3 を「完了」、差し戻しなら Step 3 を「着手中」のままとして備考に未解決事項を要約する。
- 差し戻しの場合は、メインエージェントが Step 2 を「着手中」に戻してから Generator に契約を修正させる。修正報告後に Step 2 を「完了」へ戻し、Step 3 の再レビューを行う。承認されるまで繰り返す。
- Step 3 が「完了」になってから実装へ進む。

### 4. Generatorによる実装

- メインエージェントが Step 4 を「着手中」に更新する。
- Generator に「承認された Sprint N の契約に基づき、機能とUIを完成させてください」と指示する。
- Generator は仕様に沿った一貫したビジュアル方針を決め、見た目まで実装する。
- Generator の報告と成果物を確認し、完了ならメインエージェントが Step 4 を「完了」に更新してから評価へ進む。未完了なら「着手中」のまま残タスクを書き、評価へ進まない。

### 5. Evaluatorによる最終判定

- アプリが起動済みであることを確認する。
- メインエージェントが Step 5 を「着手中」に更新する。
- Evaluator に「Sprint N を評価してください。アプリURL: [URL]」と指示する。
- Evaluator の報告を受け取ったら、メインエージェントが進捗 README を更新する。
- 合格なら Step 5 を「完了（合格）」にし、一覧の状態も「完了」にする。
- 不合格なら Step 5 を「着手中」のままとして備考に未解決事項だけを要約し、機能・デザインの問題をすべて Generator に差し戻す。

### 6. 不合格時のフィードバックループ

- メインエージェントが Step 4 を「着手中」に戻し、備考へ残タスクを記載してから Generator に修正を委譲する。
- Generator の修正報告後、メインエージェントが Step 4 を「完了」に戻し、Evaluator の最終判定を再実行する。
- 3回連続で不合格になった場合はループを停止し、Step 5 を「着手中」のまま最新の未解決事項を記載して、状況をユーザーへ報告し方針を確認する。

## 継続的な見直し

モデルのバージョンアップ時は、各エージェントの制約を1つずつ取り除いてテストし、品質が落ちない制約を削除する。新しいモデル能力で達成できることがあれば追加する。複雑さは必要性に応じてのみ加える。

## 前提

Evaluator は利用可能なブラウザ操作手段を使用するため、評価時には対象アプリが起動している必要がある。
